Wishlist mini-app — дизайн

Telegram mini-app с вишлистом на дни рождения · открытый проект · 2026-11-16 · статус: на утверждении

1. Зачем и для кого

Владелец раздаёт друзьям и семье в Telegram-чатах ссылку на бота, когда его спрашивают «что тебе подарить». Гости открывают mini-app прямо в Telegram, без регистрации, смотрят желания, бронируют подарок (чтобы не купили одно и то же) и при желании скидываются на дорогой. Список живёт из года в год: каждый день рождения — отдельный «раунд».

Проект открытый: любой может развернуть свой экземпляр одной командой docker compose up. Один экземпляр — один владелец.

2. Цели, не-цели, анти-цели

ЦелиНулевой порог для гостя (открыл ссылку — видит список). Сюрприз для именинника сохраняется. Лёгкое приложение, которое открывается на слабой связи. Простой самостоятельный деплой.
Не-целиПлатежи (взносы «в складчину» — обещания, а не деньги). Мультитенантность и SaaS. Работа вне Telegram. Отслеживание цен, напоминания гостям от бота, автосброс брони (это v2).
Анти-целиИменинник случайно узнаёт, кто что дарит. Утечка личных данных (токен бота, ID, имена) в репозиторий. Приложение, которое тянет мегабайты JS или внешние картинки.

3. Ограничения и среда

  • Хостинг: Mac mini владельца (Израиль), Docker (linux/arm64), SQLite на смонтированном volume. Белого IP нет.
  • Публичный вход: Tailscale Funnel (решение владельца). Funnel работает на хосте и проксирует на опубликованный порт контейнера. Гостям Tailscale не нужен. Гости из РФ единичные и используют VPN. Если позже понадобится, фронтом можно поставить VPS, дизайн этому не мешает.
  • Бот: long polling, Funnel нужен только для mini-app.
  • Процесс разработки (правила владельца): RED-GREEN (сначала падающий тест), запись в CHANGELOG в каждом изменении, документы для GitHub (README, SECURITY, CONTRIBUTING) в Markdown как у Iris, диаграммы в SVG.
  • Публичный репозиторий не создаётся и ничего не пушится без отдельного разрешения владельца. В коммитах только .env.example.

5. Архитектура

Telegram-клиент гостя
   │  открывает https://<mini>.<tailnet>.ts.net  (Funnel, 443)
   ▼
Tailscale Funnel ──► host:PORT ──► контейнер
                                    ├─ Hono: статика SPA + REST API (/api)
                                    ├─ grammY: бот (long polling → Telegram)
                                    ├─ Планировщик: курсы валют, ночной бэкап
                                    └─ SQLite + /data/images  (volume)
  • Авторизация: клиент шлёт initData от Telegram, сервер проверяет подпись HMAC токеном бота и срок давности. Владелец определяется по OWNER_ID. Роль проверяется на сервере, а не скрытием кнопок.
  • Конфигурация (.env): BOT_TOKEN, OWNER_ID, PUBLIC_URL, BIRTHDAY (MM-DD), CURRENCIES (по умолчанию RUB,ILS,USD,EUR), DEFAULT_CURRENCY, DATA_DIR.
  • Фронтенд: Preact, малый бандл, тема и цвета берутся из Telegram (светлая/тёмная), тактильный отклик на брони.
  • i18n: ru и en, язык по language_code Telegram, переключатель вручную, каталог строк расширяем.

6. Модель данных (заложена сразу под все функции v1)

  • rounds — раунды (день рождения): год, дата, статус open | revealed. Один открытый раунд в каждый момент. Нужна для «раскрытия» (1), но закладывается в M1, чтобы не мигрировать позже.
  • items — подарок: название, описание, ссылка(и), цена и исходная валюта, картинка, priority (3 уровня), note (размер, цвет), status (draft | published | received | archived), group_funding (флаг складчины).
  • claims — бронь/взнос: item_id, round_id, user_id, имя на момент брони, kind (full | share), amount (для складчины), время. Бронь «целиком» и взносы — одна таблица, чтобы функция (2) не ломала схему.
  • rates — кэш курсов, settings — прочее. Миграции версионируются.

7. Правила видимости (главный инвариант)

Для владельца любой ответ API не содержит данных о бронях (ни имён, ни статуса «забронировано», ни прогресса складчины) до раскрытия. Это проверяется тестами на уровне API. Подарок выглядит одинаково, брони он или нет.
  • Гости: видят опубликованные подарки, статус брони и имена забронировавших (чтобы договориться о совместном подарке). Бронь снимает только её автор.
  • Черновики: видит только владелец.
  • Раскрытие: владелец жмёт «Подвести итоги» в день рождения или после. Это переводит раунд в revealed, показывает кто что подарил, владелец отмечает «получено». Полученные уходят в архив, невыбранные и «забронировано, но не вручено» возвращаются в список со сброшенной бронью. Открывается новый раунд.
  • Скрытие брони — гарантия интерфейса и API, а не криптографии. Владелец с доступом к серверу и файлу БД теоретически может её прочитать. Цель — защитить от случайных спойлеров, а не от самого владельца. Это записывается в SECURITY.md. Бэкап (7) содержит брони по той же причине.

9. Тестирование

  • RED-GREEN: тест, падающий по ожидаемой причине, затем минимальный код.
  • Юнит и интеграционные тесты API на Vitest с временной SQLite. Фиктивные initData подписываются тестовым токеном.
  • Обязательные наборы: проверка подписи и срока initData; инвариант «владелец не видит брони» (по всем ответам API); гонки при брони и взносах; SSRF (приватные адреса, редиректы, схемы); конвертация валют и округление.
  • Компоненты и e2e (Playwright) для ключевых сценариев гостя и владельца.

10. Что оставлено исполнителю

  • Выбор провайдера курсов (должен знать RUB и ILS; ЕЦБ рубль не публикует), слой доступа к БД (Drizzle или чистый SQL), точные размеры и качество WebP.
  • Визуальный стиль mini-app, баннер и иконка. Нужны макеты. Решаем отдельно перед M1.
  • Название проекта: рабочее wishlist-bot, переименование до публикации.

11. Решения, принятые мной (проверь при чтении)

  • Раскрытие запускает сам владелец кнопкой, и только в день рождения или позже (а не автоматически).
  • Складчину включает владелец для конкретного подарка. Сумма вносится в валюте подарка, обещания без платежей.
  • Гости видят имена забронировавших, владелец не видит ничего.
  • Публичный список без белого списка: доступ у всех, у кого есть ссылка.
  • Только владелец вызывает загрузку по ссылке (так SSRF доступен только аутентифицированному пользователю).
  • Лицензия Apache-2.0, как у Iris.
  • Спецификации и планы лежат в docs/superpowers/ на русском; перед публикацией репозитория решим, оставлять их или убрать.
